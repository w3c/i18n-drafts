How to trim text correctly

Intended audience: Content authors

Every line of text in CSS sits inside a line box. The line box's height comes from the font's ascent and descent metrics plus half-leading, which is the extra space line-height adds equally above and below the text. Fonts deliberately make ascent and descent generous so that accented capitals, descenders and stacked diacritics fit.

The result is that the visible top of a block of text (for example, the top of the capital letters) almost never lines up with the top of its box. This causes three familiar problems:

  • A button label that is mathematically centered looks too low.
  • The visible gap between a heading and the paragraph below it is larger than the margin you set.
  • Text next to an icon or image never lines up with it exactly.

Developers used to fix this with negative margins tuned by eye for one particular font. That fix breaks when the font changes, fails to load, or is replaced by a fallback font. text-box fixes the problem using the font's own metrics, so the result adapts to whichever font is actually rendered.

You can see the effect directly in the demos. Because the trimming uses font metrics, the exact amount of space removed depends on the font your browser uses.

Basic trimming is supported by Blink, Gecko and WebKit browsers, but support for individual edge keywords varies. In particular, the Japanese example relies on ideographic metrics that are currently supported only by Gecko. See browsers for version information and sources.

Does it work? Blink, Gecko and WebKit browsers support all four values for block containers. Browsers without support ignore the declaration and leave the text untrimmed.

The first keyword sets the over edge. The second sets the under edge.

Over-edge keywords Meaning
text The font's text-over metric (ascent).
cap Cap height (OpenType sCapHeight).
ex x-height (OpenType sxHeight).
ideographic Ideographic over edge, the CJK em box (OpenType idtp).
ideographic-ink Ideographic ink over edge (OpenType icft).

Under-edge keywords Meaning
text The font's text-under metric (descent).
alphabetic The alphabetic baseline.
ideographic Ideographic under edge (OpenType ideo).
ideographic-ink Ideographic ink under edge (OpenType icfb).

The initial value is auto. Browsers currently treat it as text.

With the ex over edge, the box is trimmed to the x-height, so the capital "H" extends above the edge of the box. It moves the edge of the box, but does not clip the text.
.box-both { text-box-trim: trim-both; }

.edge-text { text-box-edge: text text; }
.edge-cap  { text-box-edge: cap alphabetic; }
.edge-ex   { text-box-edge: ex alphabetic; }

Does it work? Blink, Gecko and WebKit browsers support auto, text, cap, ex and alphabetic. Only Gecko currently supports ideographic and ideographic-ink. In Blink and WebKit, a declaration containing either ideographic keyword is ignored.

text-box: the shorthand

The shorthand sets text-box-trim and text-box-edge at the same time, and it behaves differently from most shorthands when you leave out the trim value.

.box-normal {
  /* trim: none, edge: auto */
  text-box: normal;
}

.box-shorthand {
  /* trim omitted, so the trim becomes trim-both */
  text-box: cap alphabetic;
}

When you leave out the trim value, the shorthand sets it to trim-both, not to the initial value none, and this is intentional.

Does it work? The text-box shorthand is supported by Blink, Gecko and WebKit browsers. Its edge keywords have the same support as those of text-box-edge, so a shorthand declaration containing an unsupported keyword is ignored as a whole.

Choosing an edge for your script

The edge keywords are not interchangeable across scripts. cap and ex are based on the case metrics of Latin, Cyrillic and Greek, while alphabetic is the baseline on which those scripts normally sit. Other scripts align text to different points, and in some cases the font does not provide a matching metric at all.

The following table gives a starting point.

Script Edge to use Notes
Latin, Greek, Cyrillic cap or ex over, alphabetic under cap fits capitals; ex fits lowercase. Neither contains descenders or marks above the letters. Use text when those must stay inside the box.
Han, Hiragana, Katakana, Hangul ideographic or ideographic-ink on both edges ideographic is the design edge, normally the edge of the em box. ideographic-ink is the ink edge.
Devanagari, Bengali, Tibetan text over, text or alphabetic under The ideal top is the hanging baseline. A hanging value has been resolved for text-box-edge but is not shipped yet, so text is the safe fallback.
Arabic, Hebrew, Thai text over, text or alphabetic under No case distinction, so cap and ex do not correspond to a reliable top edge. Tall marks may extend beyond the box.
Mixed scripts Per script run, using :lang() Metrics come from the first available font, so make the script font first for the text being trimmed.

A global reset such as * { text-box: trim-both cap alphabetic; } is not safe for multilingual content: it applies Latin case metrics to every script. Set the edge per language or per component instead.

Scripts without case

Arabic, Hebrew and Thai do not use case in the Latin sense, so cap and ex have no reliable visual meaning. The visual top of a line is not consistently at either metric; it may fall between them, and tall marks can go higher. The specification also notes that the relevant OpenType metric is missing for Hebrew. Use text for the over edge, and text or alphabetic for the under edge. If the text has tall vowel signs or tone marks, check that they do not collide with the line above or with the edge of a tight background.

Setting edges per language

text-box-trim and text-box-edge are separate properties for a reason. text-box-trim does not inherit, so trimming is opt-in for each element. text-box-edge is intended to inherit, so a script-specific edge can be set once for a language subtree and used by every element that opts in to trimming. Browser support for that inheritance is still uneven, so for now set the edge on the element that contains the text, or test the inherited pattern in the browsers you support.

:lang(ja) { text-box-edge: ideographic; }
h2:lang(ja) { text-box-trim: trim-both; }

This is also the practical way to handle a mixed-language page: mark up language changes with lang, then use :lang() to select the edge and the font for each run.

Recommended patterns

Visually centered button or badge (Latin UI)

The line box is taller than the capitals and descenders, so part of the padding you set is on empty space. Trimming the label makes its box fit the letters, so the padding becomes the gap you see.

.button {
  display: inline-flex;
  align-items: center;
  padding: 0.75em 1.25em;
  border-radius: 0.5em;
  background: #0b6e7f;
  color: #fff;
}

.button > .label {
  text-box: trim-both cap alphabetic;
}

.badge {
  display: inline-block;
  padding: 0.35em 0.7em;
  border-radius: 1em;
  background: #ffe08a;
  color: #3a2c00;
  text-box: trim-both cap alphabetic;
}

Notice that the trim is on the label, not on the flex container, because trimming does not pass into flex items.

Japanese text aligned with an image edge

Text next to an image sometimes need to align with the top of the image. The ideographic-ink over edge trims the first line to the font's ideographic ink metric (icft), instead of to its ascent, so the text can meet the top of the image.

.media-title:lang(ja) {
  text-box: trim-start ideographic-ink ideographic-ink;
}

Does it work? This example works in Gecko browsers from Firefox 154. Blink and WebKit browsers do not support ideographic-ink, so they ignore the text-box declaration and both panels remain untrimmed.

Browser support

The versions below are the first releases with basic support for trimming block containers. They do not imply support for every edge keyword.

We will try to update the article as support changes.

Browser engine Basic support from Browsers using that engine
Blink Chrome 133 Chrome, Edge, Brave, Opera, Vivaldi, etc.
Gecko Firefox 154 Firefox, Tor Browser, etc.
WebKit Safari 18.2 Safari, etc.

Support for trimming inline boxes differs from support for block containers. Gecko supports inline trimming from Firefox 154. Blink does not support it, and WebKit supports it from Safari 26.5 in horizontal writing modes only.

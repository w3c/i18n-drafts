Date formats

Question

How should I prepare web pages to display dates and times for international users?

The best practice is not just about picking a display format. First you need to know what kind of value you have: an exact moment in time, a calendar date, a local wall-clock time, a recurring anniversary, or a duration. Once that is clear, you can store the value correctly and format it for the right audience.

Answer

Separate machine-readable data from human-readable presentation. Do not make one string do both jobs. Keep dates and times in an unambiguous form for storage and interchange, then format them at the last moment according to the language of the page or the user's chosen locale.

Recommendation One: Store machine-readable values

Keep source data in a format that is unambiguous. If you store 03/04/2026 in a database or data file, nobody can know later whether that means 3 April or March 4.

The stored value should match the kind of temporal data you actually have.

  • An exact moment: use an ISO 8601 / RFC 3339 date-time with an offset or Z, for example 2026-03-19T14:30:00Z.
  • A calendar date with no time zone, such as a birthday, holiday, due date, or publication date: store only the date, for example 2026-03-19.
  • A wall-clock time such as doors open at 19:30: keep it as a local time value rather than silently turning it into a timestamp.
  • A recurring value such as an anniversary: do not coerce it into a one-off timestamp.

In HTML, use the time element to carry the machine-readable value.

Do not invent a time zone for a date-only value. A publication date or birthday is often a floating date, not midnight UTC.

Avoid parsing a date-only string with Date in JavaScript when you mean a calendar date. new Date('2026-03-19') creates a timestamp, which can later display as the previous or next day in another time zone.

Recommendation Two: Format for people, in context

What you display should fit the language and locale of the page or application. For static prose, the clearest answer is often to write the month name and a 4-digit year, such as 19 March 2026.

In modern JavaScript, use Intl.DateTimeFormat or a Temporal object's toLocaleString() method.

When an exact time matters, include the time zone or offset. When only the date matters, do not invent a time. If your audience may expect a non-Gregorian calendar or different digits, let the formatter provide that presentation instead of hard-coding Latin digits and Gregorian month names.

Recommendation Three: Use the Accept-Language HTTP header only as a hint

The HTTP Accept-Language header and browser locale settings can help you choose an initial formatting locale, but they do not tell you everything you need to know. They do not reliably tell you the user's region, time zone, preferred calendar, or whether the page should follow the language of the content rather than the device.

For example, showing Japanese-style dates inside an English article usually looks wrong, even if the reader's browser prefers Japanese. In many cases the linguistic context of the page matters more than the browser default. See Accept-Language used for locale setting for more detail.

If your application personalizes dates and times, let the user override the initial choice and remember that preference.

Modern JavaScript: use Temporal

The legacy JavaScript Date object mixes several concepts together and is easy to misuse. Temporal separates them, which makes date, time zone, and calendar handling much safer.

  • Temporal.Instant for an exact moment in time.
  • Temporal.ZonedDateTime for an exact moment shown in a specific time zone and calendar.
  • Temporal.PlainDate for a date without a time or time zone.
  • Temporal.PlainTime for a wall-clock time without a date.
  • Temporal.PlainMonthDay for recurring month/day values such as birthdays.
  • Temporal.Duration for elapsed time.

As of March 2026, Temporal has reached Stage 4 in the TC39 process and is shipping in Chrome 144+ and Firefox 139+, with Safari expected to follow. For unsupported browsers and Node.js runtimes, use a polyfill such as @js-temporal/polyfill.

Summary

Store dates and times in an unambiguous machine-readable form, and format them separately for display.

Prefer locale-sensitive formatting, and avoid ambiguous all-numeric dates when readers may misinterpret them.

For JavaScript, use Intl for formatting and Temporal for new date/time logic. Treat Accept-Language as a starting hint, not as the whole answer.

By the way

HTML already provides a time element for machine-readable dates and times. That helps scripts, search engines, and assistive technology, but it does not automatically choose the right human-facing format. You still need to decide whether the page should follow the document language, the user's chosen locale, or an application-specific convention.
